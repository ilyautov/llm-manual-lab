# Практикум

Перед каждым запуском запишите ожидаемый результат. После запуска сравните ожидание с трассой, а не только с финальной фразой. Команды выполняются из корня проекта.

## 1. Один шаг обучения

1. Откройте `src/toy-model.ts`. Для строки контекста «люблю» logits равны `[2, 1, 0]`. Какой токен модель выберет жадно до обучения? Какова вероятность правильного «чай»?
2. Запустите `npm run demo`. Выпишите три вероятности, loss и градиент до шага.
3. Проверьте обновление `z' = z - η(p - one_hot(target))` при `η=1` вручную для всех трёх чисел.
4. Почему после шага loss уменьшился, хотя самый вероятный токен остался прежним?
5. Поменяйте `learningRate` в вызове `trainSentence()` на `0.1` и `2`. Сравните вероятность цели. Затем верните исходное значение.

**Что предъявить:** таблицу `токен / logit до / p до / градиент / logit после / p после` и одно предложение о том, что именно изменилось в модели.

### 1а. Одна голова attention

До запуска посчитайте для позиции «люблю» три скалярных произведения с ключами `я=(1; 0)`, `люблю=(0; 1)`, `чай=(1; 1)`. Какие две позиции останутся после causal mask? Затем запустите `npm run attention` и выпишите масштабированные оценки, веса, сумму V, вектор после остаточной связи и вероятность «чай». Измените только вектор будущего токена на `[500,-700]` в вызове `attentionRow(1, ...)`: какие значения для позиции «люблю» обязаны остаться прежними?

**Что предъявить:** строку матрицы attention с закрытой клеткой и объяснение, почему это не полный трансформер.

## 2. Документ с новым тарифом

Запустите `npm run rag`. Сравните `withDocument` и `withoutDocument`: индекс, ID фрагмента, контекст, ответ. Определите, какое свидетельство отсутствует, когда документ не найден. Затем измените цену только внутри `TARIFF_V2` и повторите запуск.

**Что предъявить:** две трассы и вывод о том, менялись ли веса модели. Здесь LLM не вызывается, поэтому задача проверяет границу retrieval/context, а не качество генерации.

## 3. Число 42 и права доступа

Запустите `npm run orders`. Почему `model_proposal` ещё не доказывает выполнения запроса? Сравните `allowed` и `denied`. Измените дату на `2025-03-02` и получите ожидаемый счёт.

**Что предъявить:** событие разрешения или отказа, строку фильтра базы и результат. Не считайте отказавший вызов успешным нулевым результатом.

## 4. Повтор webhook

Запустите `npm run webhook` и затем `npm test`. Два отдельных процесса доставляют один `event_id` в SQLite. Объясните, почему `rowsForEvent` равен 1 и какую гарантию эта проверка **не** даёт для платежей и уведомлений.

**Что предъявить:** оба результата работников, число строк и одну непроверенную внешнюю операцию, для которой нужен отдельный тест идемпотентности.

## 5. Оценка без красивого среднего

Запустите `npm run evaluate`. Объясните, почему набор из 12 специально подобранных граничных случаев не даёт оценки доли успехов всех пользователей. Затем сравните интервалы для 10/12 и 80/100, посчитайте Recall@3 и MRR@3 по трём рангам `[1, 2, null]` и `[1, 1, 2]`. Почему reranking сам по себе не найдёт отсутствующий фрагмент?

**Что предъявить:** четыре числа метрик, предпосылки интервала и план парного сравнения двух версий системы на одних входах.

## 6. Схема и недоверенный источник

Запустите `npm run structured` и `npm run injection`. В первом опыте объясните, почему кандидат A с наибольшим logit получает вероятность 0 после маски и почему валидный JSON ещё может содержать неверный `customer_id`. Во втором отделите текст найденного документа от полномочий runtime. Какая запись в трассе доказывает отказ в записи? Какая подтверждает разрешённое чтение числа 42?

**Что предъявить:** нормированное распределение, два отказа runtime и один результат чтения. Модель в этом опыте не вызывается: вредоносные предложения заданы вручную, чтобы проверить именно границу исполнения.

## 7. Живой прогон и проверка инструкций

Пройдите [живую лабораторию](live-lab.md). До запуска запишите ожидания для тарифного фрагмента, отсутствующего документа и вызова `paid_orders`. После `npm run live` сохраните все три трассы. Затем выполните `npm run live:evaluate` и вручную разберите 12 ответов по рубрике факта, источника, границы и ясности.

Поменяйте только системную инструкцию для тарифного случая, оставив модель и набор неизменными. Сравните версии A и B по типам ошибок. Не подгоняйте инструкцию по ответам закрытой проверки: выделите часть случаев для настройки, часть оставьте для финального сравнения.

**Что предъявить:** имя и версию модели, исходную и изменённую инструкции, обе трассы, таблицу ошибок по типам, одну обнаруженную ошибку модели и границу вывода из 12 случаев.
